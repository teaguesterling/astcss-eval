Context

The undertaking

astcss is a CSS-style query language over abstract syntax trees, executed by sitting_duck's ast_select. A request like “methods of the Parser class” has one right selector, .class#Parser .fn, and the only honest test of a model's answer is to run it and compare node sets, not strings. This project builds an execution-verified eval and training set for that translation, then measures how far prompting, context and fine-tuning each get.

What a pair is

Each pair is a request, two paraphrases, a selector, a fixture it runs on, and distractors: near-miss selectors that must return a different node set. Pairs come in four tiers.

tiershapeexampleeval pairs
T1one semantic class or node type.loop · with_statement21
T2one step plus a name or attribute filter.call#sleep · .fn[name^="test_"]25
T3exactly two steps joined by a combinator.class#User .fn · .import ~ .class31
T4:has or :not(:has) on a step.fn:not(:has(.throw))31

The verifier decides what is kept

sitting_duck fails silently in both directions (unknown selector parts are ignored, some filters match nothing without error), so no pair enters either set on trust. Every candidate passes these gates:

  • Bounds: the selector returns 1–50 nodes on its fixture.
  • Load-bearing: dropping any filter or combinator step changes the node set.
  • Distractors: each parses, runs, and returns a different node set.
  • :has ground truth: the engine's answer must match a containment query computed directly on the tree (sitting_duck #133 leaks keyword tokens into :has).
  • Held-out eval: no training pair repeats an eval request, or an eval answer from T2 up.
  • No duplicates: no two pairs on a fixture select the same nodes.

Data, hardware, goals

  • Eval: 108 Python pairs on two held-out fixtures, scored by execution match.
  • Training: 918 verified pairs in nine languages on 20 training fixtures. Capped at 8 per (request template, selector shape), that is 820 pairs, 297 shapes, 2,205 training rows with paraphrases, and 85 validation pairs.
  • Tiiny device: an NPU box serving chat models through an OpenAI-compatible API; one model resident at a time; thinking switched off per request.
  • longbottom: an RTX 2080 Ti (Turing, no bfloat16) for QLoRA and local evaluation.
  • Plan: evaluate on the device through prompt and context construction; fine-tune locally; import a tuned model to the device last. The import path is currently blocked on the device side.

Pinned engine

Every number from stage 5 on is scored with one frozen sitting_duck build and the fix/127-combinator-steps macros. With main's macros the same build returns 0 rows for every two-step selector, which briefly made T3 look like 0 of 31 for every model. qualify.py oracle confirms the pinned pairing: references 100 %, first distractors 0 %.

Method · how the corpus is built, and what it has to survive

How a pair is made and checked

The eval is only worth its numbers if a pair cannot enter it by being plausible. Nothing here is accepted because it looks right: every pair is executed against real code, and every claim about what a selector means is computed twice and compared.

Six gates, and a pair must pass all of them

gatewhat it rejects
Boundsa selector returning 0 nodes, or more than 50. Zero is the silent-failure shape the engine produces for an unsupported construct; the upper bound keeps “every function in the repo” out.
Load-bearinga modifier that changes nothing. Drop each #name, each [attr], each pseudo-class and the first combinator step in turn: if the node set is unchanged, the pair teaches a decoration.
Distractorsnear-miss selectors that must parse, run, and return a different node set. A distractor matching the reference means the request does not pin the answer.
No duplicatea node set already frozen by another pair on that fixture. Two questions with one answer teach the model the answer, not the question.
Held-out evala training pair repeating an eval request, or an eval answer from tier 2 up. The sibling batch alone hit this 7 times in 8 rejections.
Request determines the selectorwording that cannot pick the answer without seeing the fixture: a prefix claim the filter falsifies (“starts with cmd” for ^="_cmd_"), an unstated name filter, a fixture-defined name described only by role, “immediately” written against ~.

Then the wording itself is checked: a second model reads each request back into a selector, and a wording that lands on one of the pair's own distractors is dropped. The suite lost 111 wordings and 13 whole pairs that way; the sibling batch 70 and 13.

Two answers for every selector

sitting_duck's ast_select fails silently in both directions, so the engine cannot be the only authority on what a selector means. oracle.py is the second: the documented semantics, computed in Python over the node table the engine itself exports. Both answer every selector, and the comparison decides what happens to the pair.

agreeThe pair is verified and its node set is frozen as the reference.
disagree, explainedA filed engine defect covers the difference: the pair is held pending_engine:<issue> with the documented node set, never scored, and revisited when the engine changes.
disagree, unexplainedRejected. Either the oracle is wrong or there is an unfiled defect, and both deserve a look before a pair enters the corpus.

That third arm is where three of this project's six upstream issues came from: the pairs failed, the failure had no explanation, and the explanation turned out to be in the engine.

Selector first, words second

Asking a model to invent pairs from source files produced about 13 % that survived verification. Composing the selector from the tree first, and asking a model only for the English, produced 343 of 352. Every batch since is built that way:

extractOne engine session per fixture: every node's parent, sibling index, descendant count, name, flags and parameter count, plus each card class's exact node set.
enumerateCompose selectors in Python, predict their node sets, keep only in-bounds, load-bearing, non-duplicate, non-eval ones, and weight the shapes training lacks.
wordA device model writes a typed request, a spoken one and a question, from the selector plus a plain-English gloss and two matched source lines.
verifyThe gates above, with the oracle deciding and the engine confirming each reference.
back-translateA second model reads each wording back; wordings that land on a distractor are dropped.

Two variants reuse the same machinery. Siblings promote the distractors that pairs already carry — each was proven to select something different, so it is a verified question waiting for words. Class-form alternatives take a pair that names a grammar type and add its counterpart in the card's vocabulary (case_item + case_item beside .if + .if), keeping both so the corpus teaches the distinction rather than replacing it.

Making verification affordable

Every ast_select_from call costs about 6 s of planning before it reads anything — the same on a 77,730-node table and a 1-row one, and PREPARE does not amortize it (sitting_duck #160). Verification time is therefore the number of distinct engine calls, and three changes attacked exactly that:

changeeffect
Result cache keyed on engine binaries, macros, fixture contents and selectoridentical queries run once, ever; a re-verify after a wording change costs seconds
Oracle-first gates: the oracle answers relaxations and distractors, the engine confirms one reference per pairaudit-r1 16m41s → 4m57s, prefix-c1 41m52s → 4m36s, verdicts identical on 581 replayed pairs
Per-query retry when a CLI process dies mid-scriptone selector that exhausts memory used to reject dozens queued behind it: suite 1 lost 522 candidates, the sibling batch lost 1

The oracle-first switch was validated rather than assumed: ten committed batches were re-run on the engine that verified them, 581 accepted pairs in and 581 out, no reference changed, every rejection difference traced to a gate added later or an id retired since.

Provenance, so numbers stay comparable

  • The engine is pinned and recorded. Every batch stores the CLI path, extension mtime, checkout commit and macro checksum that verified it. A build change is visible in the data, not a mystery in the scores.
  • References are frozen node sets, not live queries. Scoring compares a model's answer against a stored sha256 of file:node_id, so a score never depends on the engine being up, or the same.
  • A second pin, on purpose. When main fixed two defects, a second build was pinned only to re-verify pairs held pending; the original pin still scores every model, so nothing already measured moved. That is how 230 held pairs became verified without disturbing a single reported number.

Two traps worth naming

Execution rate is not quality. A model answering in prose still “executes”: a bare word parses as a type selector. Across the no-card arms, exec rate ranged 46–100 % while match stayed at 0. Only match means anything once the format breaks.

Pending is not rejected. A pair whose documented answer differs from the engine's because of a filed defect is kept with its documented node set and scored by it. Treating those as failures would have thrown away 2,700 tier-5 pairs; treating them as verified would have taught the model the engine's bugs.

Primer · adapted from the session's lesson, updated with what later runs measured

QLoRA, from first principles

QLoRA stands for Quantized Low-Rank Adaptation: learn a small correction to a model's weights (LoRA, Hu et al. 2021) while the frozen base sits in 4 bits (Dettmers et al. 2023). Together they fit a 9-billion-parameter fine-tune on one consumer GPU.

Why full fine-tuning is out of reach

Memory per parameter with Adam, before activations
itembytes / paramfor 9B params
weights, fp162~17 GiB
gradients, fp162~17 GiB
Adam moments, fp328~67 GiB
total12~100 GiB

The card has 11 GiB, about 1.4 of which the desktop holds. Full fine-tuning needs roughly ten times that.

LoRA: learn a small correction

A linear layer computes y = W·x. LoRA freezes W and adds a low-rank update:

y = W·x + (α / r) · B·A·x
  • A is r × din, B is dout × r. We use rank r = 16 and α = 32, so updates scale by 2.
  • B starts at zero: at step 0 the model is exactly the base.
  • For one 12,288 × 4,096 MLP projection, LoRA trains ~262k numbers instead of ~50M (0.5 %). Across every linear layer of Qwen3.5-9B: 43.3M of 9.0B parameters (0.48 %).
  • After training the correction can be merged (W ← W + (α/r)·B·A) into an ordinary checkpoint, which matters because the Tiiny imports only full safetensors.

Quantization: the frozen base in 4 bits

  • NF4: 16 levels placed at the quantiles of a normal distribution, dense near zero where trained weights cluster.
  • Block-wise scales: one scale per 64 weights, so an outlier only degrades its block.
  • Double quantization: the scales themselves stored in 8 bits, ~0.37 bits per parameter saved.
  • Compute dtype: each 4-bit weight is dequantized for its layer's forward pass. Turing has no bfloat16, so compute is float16.
  • Gradients flow through the dequantized weights; only A and B are updated.

What it took on this card

decisionwhy, as measured
Embedding table on the GPUThe lesson moved it to the CPU to save 1.9 GiB. The offload added 478 hooks and made each forward ~3× slower, so it went back.
No prepare_model_for_kbit_trainingIt upcasts every unquantized tensor to fp32; on the 248k-row embedding that is a 3.8 GiB allocation and the first out-of-memory. Gradient checkpointing and input gradients are enabled by hand.

One prompt function for training and generationtune/prompting.py renders the chat template once per shape. Qwen3.5's template trims message text, Qwen3-4B-Instruct's does not; trimming is detected per tokenizer and checked byte-identical.

The data side

user:      methods of the Collector class
assistant: .class#Collector .fn                ← loss computed only here
  • Split by pair, not row: paraphrases are near-duplicates; splitting rows would measure memorization.
  • Template cap of 8: “calls to N” appears 57 times; uncapped, the model mostly learns that one shape.
  • Train and serve prompts match: an adapter is always asked in exactly the format it was trained on.
  • Judge checkpoints by execution match on the eval, not validation loss. Stage 6 shows why: the 9B's loss kept falling from epoch 1 to 2 while its score dropped.

From adapter to device, later

Merge into the full-precision base, save in the base's original Qwen3_5ForConditionalGeneration layout (vision tower and preprocessor configs included, since the device toolkit matches on it), re-run the eval on the merged weights, then tiiny import from a private Hugging Face repo. That last step waits on the device's import catalog, which currently reports invalid.

Design · rationale · results

Experiments

Stages run in order; each one's question came from the one before. Scores are execution match on the 108 eval pairs unless noted. Flips (+gained / −lost) compare an arm with its own control. Almost every arm is a single run; the only noise reference is stage 3's rerun, where a card change of 1–6 flips in 98 pairs was within noise.

Which instructions to send

stages 1–4done
Question

What does the vocabulary card, the system prompt that teaches the selector language, need to say?

Design

11 models × 40 pairs on card v1; then 4 models × 109 pairs on v1 vs v2; then per-model cards v1c, v2, v3 on 98 comparable pairs, with an exact rerun of v1 to measure noise. v1c is v1 with seven example selectors that leaked eval answers swapped for unused names.

Result
  • Card v1c: gemma-4-26B 86.7, Qwen3-Coder-30B 76.5, uncensored 9B 71.4. Qwen3.6-27B preferred v2 (92.2), level with the Haiku 4.5 control.
  • Every attempt to add guidance hurt the models that did well without it: v2's type rules flipped gemma into guessed node types (.import → import_statement), 18 regressions.
  • Most misses shared causes the card never covered: dotted node types (.with_statement matches nothing), .call#json.dumps for .call#dumps, a .mod > habit, and three-step chains the engine refuses.
  • Five eval requests were rewritten: every model gave the same reasonable, different answer (“recursive glob calls” when the call is rglob).
Reading

Card work past v1c does not pay. The remaining errors are structure, the target for examples and training.

Size ladder, trained with the card

stages 6c, 6ddone9B running
Question

Selector-first pairs

selector-first pilotdone
Question

If the tree and engine choose the selector, and a model writes only the words, do the engine-stage losses disappear and can the shape mix be chosen instead of hoped for?

Design
extractOne engine session per fixture: every node's parent, sibling position, descendant count, name and parameter count, plus each card class's exact node set.
enumerateCompose T1–T4 selectors in Python, predict their node sets, keep only in-bounds, load-bearing, new, non-eval ones; weight shapes training lacks.

verifyThe verifier's training gates; the engine's node set is compared with the prediction.

Paraphrases for training pairs now need only differ from each other; the eval keeps its stricter overlap rule (Teague, 2026-09-15).

So far
  • Extraction: 46–80 s per fixture, six fixtures in parallel.
  • Enumeration: 352 candidates in 6 seconds, 250 distinct shapes, 269 with a shape new to training; by tier T1 10, T2 96, T3 108, T4 138. Examples: while_statement:not(:has(break_statement)), .fn[params=5], .class[name$="Annotator"], .try ~ if_statement.
  • Wording: 352 of 352 worded in 16 minutes. The wordings stay close to the gloss (“variables whose names end with _flag”), so they are accurate but plain; whether that matters for training is an open question.
Then

343 of 352 candidates verified, and the engine agreed with the Python prediction on every one — the prediction layer became oracle.py, the documented semantics computed in Python over the engine's own node table, and it now decides the gates while the engine only confirms each reference. The approach scaled to all nine languages: see the tier-5 suite.

Requests that don't determine their selector

request auditdone
Question

Every arm above is measured against training data nobody had audited. A pair can only teach the mapping if the request picks out that selector without seeing the fixture. Does it?

Design

audit_pairs.request_reasons reads each text against its own selector and nothing else, and flags five defects: a prefix or suffix claim the filter falsifies or narrows, a name filter the text never states, a fixture-defined name described only by its role, “immediately” written against ~, and referential requests. Presence is matched on word boundaries with inflections, so “recon” does not count as stated by “reconciling”. Run over every training and eval wording.

Result
  • 90 of 918 training pairs carried at least one bad wording, 202 texts in all; each was reworded to state the literal, the originals retired, and the replacements re-verified as batch audit-r1 (90 of 90 accepted).
  • The defect concentrated in one shape: .fn[name^="_cmd_"] asked as “functions starting with cmd”. A model cannot know about the underscore, so the pair taught a guess.
  • A contrast batch of 184 literal prefix/suffix candidates was added, 150 of them with no underscore at all; 127 passed the gates.
  • The rule is now a gate: pilot.py rejects training candidates that fail it and the generator drops such wordings before they reach a dataset.
Reading

This is the one result that changes older numbers rather than adding to them: every score above was trained on a corpus with 90 bad pairs in it. The reworded ids also change which pairs land in validation, since the split hashes the id.

Reading

Examples are worth nothing to an adapter, static or retrieved, and the copy baselines prove the retrieval pool is relevant rather than useless — the adapter already knows what those examples teach. The real finding is the cliff: the card is a task trigger, not reference material. Two epochs on rows that all carried it taught “card present → emit a selector”. The fix is in the data, not the prompt: --system mixed varies the prompt per request (card 50 %, bare [lang] tag 25 %, nothing 25 %) so the request triggers the task. One more trap: those prose answers scored 94–95 % “executes”, because a bare word like raise parses as a type selector. Exec rate means nothing when match is zero.

Class-form alternatives

classalt1done
Question

Many pairs name a grammar type (catch_clause:has(.call)) where the card has a class for it (.catch:has(.call)). The class form reads better and carries across languages. Should the corpus switch?

Design

Neither switch nor duplicate: add. For every accepted pair whose selector names a type, compose the same shape in class vocabulary and keep the original as the candidate's contrast, so the wording stage is told to make the difference explicit. Where the bare class form runs past the 50-node bound, scope it to the named function or class the original's nodes sit in rather than reverting to the type.

Result

61 pairs across seven languages — 57 verified, 4 pending on #133, none rejected. Of 281 type-form pairs only 90 have a class form that selects the same nodes, so these are mostly new questions: .loop covers for and while, .class covers tables and views, .fn covers lambdas.

Two defects surfaced. The wording model echoed the card's labels across languages — “the organizations class” for a SQL table — so the rule now names each language's own nouns. And the type-specific original cannot be a distractor when both forms select the same nodes, which is exactly what the gate caught.

Reading

The pairs teach the distinction rather than replacing it: .if + .if beside case_item + case_item, each with its own frozen node set.

Where it goes next

Open questions

  • Does tier-5 training move tier 5, and what does it cost the basic tiers? The suite has 1,416 verified tier-5 pairs and the 0.8B scores 30.9–34.5 there today. Arms: card v1 plus tier-5 pairs, the mixed-prompt dataset, and a short tier-5 block, with the 108-pair score as the guard.
  • Does prompt-variety training remove the card dependency? The trained 0.8B scores 0.0 without its card. --system mixed trains behind card, tag and bare request; if the score holds, the ~700-token card becomes optional at serving time.
  • Do the recovered candidates change the yield? 522 tier-5 candidates were rejected on engine resource errors rather than merit, and failures are never cached, so a re-run retries exactly those.
  • Does the 9B trained with the card beat the 4B's 89.8? Still unrun; the GPU went to the 0.8B work.
  • Noise: nearly every arm is one run. Stage 7a put e2 seed noise at about one pair, so 2–4 point gaps still need repeats.
  • Review decisions: 66 notes from Claude's pass over 1,215 pairs are waiting — 38 wordings, 11 drops, 2 selector fixes — and they change which pairs train.
  • Deployment: merge, re-evaluate the merged weights, and import to the Tiiny when its catalog recovers. Device and local runtimes may still disagree on identical weights.
  • Card v1c's .import ~ .var example matches nothing in Python and should become .import ~ .fn.
